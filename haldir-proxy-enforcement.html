Enforcement model

Haldir Proxy Enforcement

You said proxy-mode enforcement is the right default and that studio tools can still shell out. Both are true. Here is where the line actually falls, and the one hole in it that your allowlisted-hosts case would hit.

What the proxy governs

Haldir sits between the agent and the MCP servers it calls. A tool call goes to Haldir first, gets evaluated against the session's policy, and is either forwarded upstream or refused. Policy is evaluated per call — nothing is cached at session creation, so a change takes effect on the next call, not the next session.

What that buys you, concretely:

Enforced on the proxied path

  • Which tools may be calledAllow-list, deny-list, or a per-tool block, scoped to the session.
  • How much may be spentSpend caps on the session; over-budget calls are refused, not logged after the fact.
  • How often, and whenRate limits and time windows per policy.
  • That it is on the recordEvery proxied call lands in the hash-chained audit log.
  • That revocation sticksRevoking a session closes every granted scope on the very next call.

Outside the proxy

  • A shell the agent can reach itselfbash, an exec tool, a file write — anything that does not route through MCP.
  • Direct network egressAn SDK calling an API without going through the proxy.
  • The host's own capabilitiesWhat the sandbox the agent runs in already permits.

You are right that this is the right default, and you are also right about the consequence: an agent with its own shell is not governed by a proxy it can walk around. That is not a bug in the proxy — it is the shape of the boundary. Haldir governs the MCP path. Making the boundary hold means the deployment does not hand the agent an ungoverned exec tool, or runs it somewhere that cannot reach one.

Worth saying plainly, because a governance tool that overstates itself is worse than one that does not exist: Haldir cannot enforce that from the inside. It can only tell you what it saw, and be honest that there is a path it did not.

The hole your case would find

There is no host allow-list on proxy upstreams today. Policies are evaluated over tools — allow-list, deny-list, block, spend, rate, time window — and nothing evaluates the host an upstream points at.

Registering an upstream takes a name and a URL and accepts the URL as given. It is then fetched, in the same request, to discover the upstream's tools — and the response body comes back in the reply.

We already have the guard for this, and it is applied elsewhere. Webhook registration and approval notification targets both run through a check that refuses anything that is not plain http(s) to a public address, re-checked at fetch time because a name that resolved publicly at registration can resolve to loopback by the time it is used. The proxy does not call it.

Verified, not inferred

The same loopback URL, submitted to two endpoints on one running instance, gets opposite answers. The webhook endpoint refuses it: host '127.0.0.1' … is not a public address. The proxy accepts it, fetches it, and returns part of the response body.

So this is not a theoretical gap in a policy table — it is a missing call in a code path that already knows how to make it. Your beta case is the right one, and it lands on a real defect.

Three things we did break on purpose

You named three surfaces you would attack. A fixture now drives all three against a running instance and prints the raw responses behind each verdict, so you can argue with the evidence rather than the summary. It runs locally with no account and no deployment:

Probe What it does Result
mid-call revocation Grants a scope, revokes the session, asks again — plus a never-granted scope as a control, so a gate that always says no cannot pass. Holds
timeout after commit Sends one Idempotency-Key twice — the shape of a commit whose response was lost — then reuses that key against a different body. Holds
audit read-back A fresh connection reads the chain back and verifies it, then edits a row behind the server's back to prove the verifier can fail. Holds

The retry is safe and returns the original entry rather than writing a second one; the reused-but-different key is refused with a 422 rather than silently obeyed. The third probe is the one worth your time — it edits action in the SQLite file without touching the stored hash, and verification fails with entry hash mismatch. A verifier that cannot fail is not evidence, so that direction is checked too.
